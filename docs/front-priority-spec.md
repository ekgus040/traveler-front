# Traveler Front 간단 기획서

기준 문서
- `메인개요서.docx`
- `Traveler_RoadMap_v12.html`
- 팀 대화 마일스톤 메모
- `mobility_rag` 실제 백엔드 코드

기준 원칙
- 오늘까지 꼭 만들어져야 하는 것 우선
- 백엔드에서 이미 구현된 기능 우선
- 프론트는 실제 연결 가능한 범위를 먼저 제품처럼 보이게 완성

서비스 한 줄 정의
- `LLM 및 RAG 기반의 초개인화 모빌리티 트래블 큐레이터 서비스`

개요서 기준 핵심 사용자 가치
- `Zero-Search`: 검색을 여러 번 하지 않고 한 번의 흐름으로 여행 코스를 받는다.
- `Triple Mode`: 근교 / 자차 장거리 / 타지 렌터카 세 가지 사용 상황을 하나의 서비스에서 다룬다.
- `초개인화`: 날씨, 동행자, 분위기, 방문 이력, 선호도를 함께 반영한다.
- `신뢰성`: 단순 추천이 아니라 근거와 검증 단계를 보여주는 방향을 유지한다.

## 1. 기능 간단 명세

우선순위 기준
- `P0`: 오늘 반드시 구현 / 백엔드 연동 가능 / 시연 핵심
- `P1`: MVP 직후 바로 필요한 기능 / 일부 백엔드 준비됨
- `P2`: 기획상 중요하지만 현재는 화면 선반영 또는 후속 개발

| 기능 | 설명 | 우선순위 | 백엔드 상태 | 프론트 방향 |
|---|---|---:|---|---|
| 모드 선택 | 근교 / 장거리 / 타지 3개 모드 선택 | P0 | 일부 구현됨 (`travel_mode` 방향 존재, 현재 프론트 상태 보유) | 첫 진입과 플래너에서 반복 선택 가능 |
| 추천 요청 | 질의, 날씨, 동행자, 분위기, 템포 입력 후 추천 요청 | P0 | 구현됨 (`/api/chat` SSE) | 핵심 CTA로 유지 |
| 추천 결과 스트리밍 | 추천 텍스트와 장소 결과를 실시간 수신 | P0 | 구현됨 (`/api/chat`) | 결과 페이지에서 스트림 상태 노출 |
| 방문 이력 저장 | 추천 장소를 visited로 저장하고 재추천 시 제외 | P0 | 구현됨 (`/api/session/{id}/visited`, `clear`) | 결과 저장 버튼 유지 |
| 세션 유지 | session_id 기준 대화/방문 이력 유지 | P0 | 구현됨 (Redis trip_session, chat/session clear) | 새로고침 후 같은 흐름 유지 |
| 결과 리스트 | 추천 장소 순서, 태그, 요약 표시 | P0 | 구현됨 (`place_id`, `visit_sequence`, `place_name?`) | 플랫폼형 카드 UI 유지 |
| 멀티턴 수정 | “조용한 곳으로 바꿔줘” 같은 후속 요청 | P0 | 부분 구현됨 (대화 메모리/세션 존재) | `일정 수정` 페이지 유지 |
| 장거리 출발/도착 입력 | 장거리 모드일 때 출발지/도착지 입력 | P0 | 프롬프트 레벨/계획 존재, 완전 API 계약은 약함 | 플래너에서 우선 입력 UI 제공 |
| 지도 시각화 | 추천 장소/이동 흐름을 지도에서 확인 | P1 | 실제 좌표/Polyline 계약은 약함 | 당장은 구조 중심, 추후 SDK 실연동 |
| 장거리 경유지 안내 | 휴게소/주유소/점심 POI 제안 | P1 | 문서/주석/계획 존재, 실연동 미완성 | 모드 가이드+결과 화면에서 우선 표현 |
| 날씨 반영 추천 | 현재 날씨 기반 실내/실외 비중 조정 | P1 | 구현됨 (`weather.py`, `/api/chat` 컨텍스트) | 입력값 + 결과 카피에 반영 |
| 선호도 누적 | prefs 기반 취향 저장/재활용 | P1 | 구현됨 (`prefs`, Redis) | 온보딩/향후 개인화 연결 |
| Cold-Start 온보딩 | 3~5개 질문으로 첫 취향 입력 | P1 | 직접 API는 없음, prefs 연결 가능 | 별도 온보딩 페이지 제공 |
| 신뢰도 공개 | trustScore, reasoning, executionReady, Tier 1~3 | P2 | 문서상 중요하지만 현재 API 응답 없음 | 현재는 기획/목업 페이지 유지 |
| 계절/축제 3-Layer | 날씨(L1) + 계절(L2) + 축제(L3) 기반 추천 근거 | P2 | 날씨는 구현, 축제/계절 완성형은 미확인 | 문구/가이드 중심 선반영 |
| 서킷 브레이커/캐싱 | 외부 API 장애 시 폴백/속도 보완 | P2 | Redis는 있음, 명시적 제품 기능 노출은 낮음 | 사용자에겐 에러/재시도 UX로 최소 반영 |
| 명소/히든 구분 | 대표 명소와 로컬/숨은 장소 비중을 구분해 제안 | P1 | 문서/데이터 전략 존재, 완전 자동 판정은 후속 | 카드 태그/가이드 설명 우선 |
| 반응형 사용성 | 모바일/태블릿/차량 디스플레이 대응 | P0 | 프론트 단독 구현 가능 | 모든 주요 페이지 반응형 우선 |

### 오늘 기준 프론트 필수 구현 범위

#### P0 오늘 반드시 완성
- 모드 선택
- 추천 입력/요청
- 추천 결과 페이지
- 방문 이력 저장
- 세션 유지
- 멀티턴 수정
- 장거리 기본 입력 UI
- 헤더 라우팅 기반 플랫폼형 구조
- 모바일/태블릿에서도 무너지지 않는 반응형 구조

#### P1 가능하면 포함
- 온보딩
- 날씨 반영 카피/상태
- 장거리 전용 가이드
- 지도 영역 구조 고도화
- 명소/히든 태그 표현
- Zero-Search 흐름을 설명하는 홈 구조

#### P2 후속 연동
- trustScore 실데이터 연동
- 실제 경로 Polyline / 마커
- searchPoiAlong 실연동
- 축제/계절/3-Tier 실제 API 반영

## 2. 화면 설계

화면 원칙
- 대시보드가 아니라 `여행 추천 플랫폼`
- 헤더에서 주요 라우팅
- 각 화면은 역할이 분명해야 함
- 한 화면에 모든 정보를 몰아넣지 않음
- 차량용/태블릿에서도 읽히는 큰 정보 단위 유지
- 추천 이유와 이동 흐름을 사용자 관점에서 읽히게 구성

| 화면 | 목적 | 핵심 UI | 우선순위 | 백엔드 연동 |
|---|---|---|---:|---|
| 홈 `/` | 서비스 소개 + 현재 추천 상태 + 흐름 안내 | 히어로, 현재 요청 요약, 추천 플로우 3단계 | P0 | 상태값 일부 연동 |
| 온보딩 `/onboarding` | 첫 취향 수집 | 질문 카드 3~5개, 선택 요약, 완료 CTA | P1 | 현재는 로컬 상태, 추후 prefs 연동 |
| 여행 만들기 `/planner` | 추천 조건 입력 | 모드 선택, 질의 입력, 날씨/동행/분위기/템포, 장거리 출발/도착지 | P0 | 추천 요청 직전 핵심 화면 |
| 추천 결과 `/results` | 추천 결과 소비 | 결과 요약, 지도 영역, 장소 카드 리스트, `[명소]/[히든]`, visited 저장 | P0 | `/api/chat`, visited API |
| 일정 수정 `/refine` | 멀티턴 수정 | 이전 메시지, 수정 입력창, 재요청 버튼 | P0 | 세션 기반 대화 재사용 |
| 모드 소개 `/modes` | 근교/장거리/타지 차이 설명 | 모드별 설명, 장거리 플로우, 명소/히든 비중 | P1 | 기획성 화면 |
| 추천 기준 `/trust` | 추천 신뢰도 설명 | trust score, reasoning, tier 단계 | P2 | 현재는 목업, 추후 실데이터 |

### 화면별 필수 요소

#### 홈
- 브랜드 헤더
- 라우팅 메뉴
- 추천 시작 CTA
- 현재 선택된 조건 요약
- 서비스 흐름 소개
- Triple Mode 차이 소개
- Zero-Search 가치 문구

#### 여행 만들기
- 상단에 모드 선택
- 중앙에 질의 입력
- 하단에 조건 선택
- 장거리일 때만 출발/도착지 노출
- 추천 시작 버튼 1개를 가장 강하게 노출
- 날씨/동행/분위기 값이 실제 추천 품질에 영향을 준다는 설명

#### 추천 결과
- 상단: 현재 추천 제목/설명
- 좌측 또는 상단: 지도/경로 영역
- 우측 또는 하단: 장소 카드 리스트
- 저장 버튼
- 장거리 모드일 때 이동 가이드 강조
- 가능하면 `[명소] / [히든]` 성격을 카드에서 바로 구분
- 장거리 모드에서는 `이동 구간`과 `도착 후 코스`를 분리해 읽히게 구성

#### 일정 수정
- 기존 대화 로그
- 수정용 단일 입력창
- “다시 추천” 또는 “이 부분만 수정” CTA
- visited_spots가 누적된다는 점을 사용자가 인지할 수 있어야 함

## 3. 실제 구현 우선순위 요약

### 1순위
- `여행 만들기`
- `추천 결과`
- `일정 수정`
- `모드 선택`
- `visited 저장`
- `세션 유지`

이유
- 오늘 시연 가능해야 함
- 백엔드 실구현 범위와 맞닿아 있음

### 2순위
- `온보딩`
- `모드 소개`
- `장거리 전용 결과 표현`

이유
- 사용자 경험을 높임
- 문서상 중요하고 프론트 선반영 가치가 큼

### 3순위
- `추천 기준(trust)`
- `실시간 경로/Polyline`
- `축제/계절/검증 레이어 실데이터`

이유
- 기획상 중요하지만 현재 백엔드 계약이 약함
- 오늘까지는 목업/설명 화면 수준이면 충분

## 4. 최종 정리

오늘까지 제품처럼 보여야 하는 최소 범위는 아래입니다.

1. 헤더 라우팅이 있는 플랫폼형 구조
2. 모드 선택 + 입력 + 추천 요청
3. 추천 결과 리스트
4. 방문 이력 저장
5. 멀티턴 수정
6. 반응형 화면 유지
7. Triple Mode 서비스라는 인지 가능성

그 다음 우선순위는 아래입니다.

1. 온보딩
2. 장거리 모드 전용 표현
3. 추천 기준/신뢰도 설명
4. 명소/히든 태그 강화
5. Zero-Search 설명 강화

현재 백엔드 기준으로 가장 안전하게 붙일 수 있는 기능은 아래입니다.

1. `/api/chat` 기반 추천 요청/스트리밍
2. `visited` 저장/조회/초기화
3. 세션 기반 상태 유지
4. 날씨 반영 추천
5. prefs 누적 기반 개인화 확장
